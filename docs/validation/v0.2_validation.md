## Confirmed Issues

### V02-FIX-001 — Schedule Table Aggregation (P1)

Real construction schedules containing task, duration, start, and completion
columns can leave all schedule fields null. Prefer an explicit natural-language
overall period, then an explicit summary/overall row. If a clearly scoped
special-construction schedule contains only task rows, use its earliest valid
start and latest valid completion, retaining real source evidence. Never sum task
durations. Emit `duration_days` only when the source explicitly states an overall
duration. Exclude preparation, establishment, review, and material-arrival dates.

Required synthetic coverage: multi-row table; overall row plus children; no
overall duration; discontinuous work fronts; preparation-date interference;
expert-review-date interference.

### V02-FIX-002 — Metadata Field Boundary (P1)

Metadata values can consume the next label or section, including building area,
structural overview, monitoring unit, and survey/design unit. Recognize general
project, location, participant, building/structure, scale, and responsible-person
labels. Stop at the next label or chapter heading, do not append a following body
heading, but allow a genuinely wrapped company name. No company-specific rules.

### V02-FIX-003 — Project Location Semantic Confidence (P1)

Prefer explicit location labels, then strong project-space statements in the
engineering overview such as “本工程位于…”, “项目位于…”, or an explicit route
extent. Reject geological, borehole/pile, component, installation, formwork,
stress, monitoring-point, construction, beam-body, and equipment positions. If
high-confidence evidence is absent, return null.

### V02-FIX-004 — Document Title Specificity + Provenance (P1)

Prefer cover pages 1–3, then an explicit title page, engineering-overview
evidence, and body headings; headers/footers are low priority. Preserve the most
specific generic `XXX专项施工方案` or `XXX施工组织设计` title and remove a verified
project-name prefix where possible without removing professional qualifiers. Do
not use discipline-specific hard-coding. Provenance must point to the selected
real occurrence.

### V02-FIX-005 — Calculation Section Isolation (P1)

Mark calculation regions introduced by headings such as 计算书、附图及计算书、
设计计算、计算分析、验算、相关计算书. Formulae, bare standard references,
numeric/unit expressions, and calculation-object titles must not contaminate
chapters, work items, compilation basis, or materials. A later embedded
sub-document that reintroduces a complete document title, 编制依据、工程概况 and
施工工艺 structure must reopen normal extraction.

### V02-FIX-006 — Long-document Semantic Segmentation (P1)

Select method regions from construction-method/process/technology, installation,
erection, dismantling, and embedded-sub-document construction chapters. Exclude
quality, safety, civilized construction, environment, emergency, acceptance,
management, and pure-calculation regions. The repair must be structural and must
not add sample or discipline keywords.

### V02-FIX-007 — Main Work Item Semantic Scope (P2)

Work items should express construction action semantics or be explicit process
headings in a construction region. Pure floor/area names and calculation-book
titles are not work items. Existing valid action items must remain available.

### V02-FIX-008 — Standards Table Pairing (P2)

Pair standard names and codes by table row before using fallback patterns.
Support name/code and code/name order, wrapped name or code, Chinese book-title
marks, and common GB, GB/T, JGJ, JTG, CJJ and DBJ families. Reject table headers
such as “国家及” and “标准” as names while preserving existing successful parsing.

### V02-FIX-009 — Compilation Basis Scope (P2)

Primary compilation basis must come from 编制依据、编制说明及依据、依据文件 or
主要规范标准 regions. Ordinary body references, acceptance requirements,
personnel qualifications, and calculation-book references are excluded. A
complete embedded sub-document may contribute its own compilation-basis region;
results are deduplicated.

### V02-FIX-010 — Source Preference (P2)

When duplicate values exist, prefer material plans over calculations, covers over
headers/footers for document type, overview tables over later prose for project
metadata, compilation-basis tables over calculation references for standards,
and construction-process headings over calculation prose for methods. Selected
`source_page` and `source_text` must remain literal source evidence.

## Regression Protection Policy

BuildCheck-Agent uses three validation layers from v0.2.1 onward.

**Layer 1 — Synthetic Unit Tests** verifies local extraction rules, semantic
boundaries, normalization, and edge conditions with small purpose-built inputs.

**Layer 2 — Golden Regression** protects the high-value behavior already
accepted by humans for the four development regression documents. Golden files
contain only stable assertions, such as required/forbidden items, exact section
presence, selected provenance, and required standard codes. They do not contain
PDFs, full document text, analysis caches, or byte-for-byte snapshots. The
deterministic Golden runner uses minimized page-text fixtures and fails if an
external LLM is invoked.

**Layer 3 — Blind / Stress Validation** evaluates generalization to new
disciplines, layouts, nested sub-documents, and very long documents through the
release-gate smoke workflow.

Layer 3 improvements must not come at the cost of Layer 2 behavior. If a blind
or stress result improves while any Golden regression fails, the candidate must
not be released.

The Golden set covers plumbing, weak-current, high-slope, deep-excavation, and a
minimal cross-domain scaffold case. Assertions intentionally protect core
behavior rather than every optional field or the complete LLM JSON.

## Remaining Limitations

- OCR is outside v0.2.1 scope; dates absent from the PDF text layer remain null.
- Method recall in very long documents with nested calculation books and embedded
  sub-documents remains lower than in ordinary documents.
- External LLM output can still vary between forced analyses.
- Golden Regression protects selected core behavior, not byte-for-byte equality
  of the full response JSON.
