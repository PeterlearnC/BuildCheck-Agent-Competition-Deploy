# BuildCheck-Agent v0.3 Completeness Review

## 1. Scope

V0.3 Development Candidate 在 V0.2.1 `DocumentAnalysis` 之上执行施工方案完整性审查，回答应有组成部分是否存在、证据在哪里、覆盖是否充分，以及缺失时建议补充什么。

V0.3 是完整性审查，不是规范合规审查，不判断施工做法对错，不提供法律结论或施工风险评级。本阶段不包含 RAG、外部规范库、条文审查、OCR、数据库、前端或自动整改正文生成。

## 2. Architecture

处理链路为：

1. 优先读取既有 V0.2.1 analysis cache；缺失时才运行一次现有 document analysis。
2. 根据 `document_type` 选择通用或专项施工方案 profile。
3. 14 个配置化 check 复用 chapters、section presence、structured fields 和已有 provenance。
4. 规则引擎生成 status、severity、reason、evidence 和 deterministic suggestion。
5. review 以 analysis SHA-256 fingerprint 为失效依据写入独立 JSON cache。

Review 的 `force=true` 只重算 review，不会强制重跑 document analysis 或 LLM。

## 3. Review Statuses

- `PASS`：存在明确、充分证据。
- `PARTIAL`：存在相关内容，但覆盖或证据链不完整。
- `MISSING`：必需项未找到可靠证据。
- `NOT_APPLICABLE`：可选项没有适用证据，不进入评分分母。

`PASS` 和 `PARTIAL` 必须至少包含一项 evidence。`MISSING` 和 `NOT_APPLICABLE` 可以没有 evidence。

## 4. Severity

- `INFO`：完善建议。
- `WARNING`：重要内容覆盖不足。
- `IMPORTANT`：方案关键组成部分缺失。

Severity 表示完整性问题的重要程度，不是施工风险等级，当前不参与 score。

## 6. General / Special Matrix

| Checks | General construction plan | Special construction plan |
|---|---|---|
| CR-001～CR-008 | Required | Required |
| CR-009 | Optional | Required |
| CR-010～CR-012 | Required | Required |
| CR-013～CR-014 | Optional | Optional |

Optional 不等于永远不适用：充分 evidence 为 `PASS`，部分 evidence 为 `PARTIAL`，无 evidence 才为 `NOT_APPLICABLE`。

## 7. Score Formula

- PASS = 1.0
- PARTIAL = 0.5
- MISSING = 0
- NOT_APPLICABLE 不进入分母

`completeness_score = round_half_up(points / applicable_checks × 100)`。

Severity 暂不加权，保证评分透明可复算。

## 8. Evidence Policy

Evidence 来源限定为 `chapter`、`field`、`section_presence` 和保守的 `text` 类型。优先使用既有 chapters、structured fields 及真实 provenance，不为 review 重新扫描 PDF 或调用 LLM。

- 已有页码原样保留。
- 无法定位时 `source_page=null`，不得制造页码。
- section presence 没有独立页码时保持 null，并尽量同时保留可定位 chapter。
- standards 或 compilation basis 中出现“验收规范”，不能单独证明方案存在验收安排。
- 监理单位或监控单位不能单独证明存在工程监测方案。

## 9. Cache Behavior

Review cache 位于 `backend/data/reviews/completeness/{document_id}.json`，运行时 JSON 被 Git 忽略，仅提交 `.gitkeep`。

缓存保存 `review_version=v0.3`、document ID、稳定 JSON 序列化后的 analysis SHA-256 fingerprint 和 review。只有版本、document ID、fingerprint 均匹配时才返回 `cached=true`。analysis 改变、cache 损坏或版本不匹配时自动安全重算。

## 10. Golden Review

独立 Golden Review 位于 `backend/tests/golden_reviews/`，使用匿名化最小 analysis fixture，只保护 profile、关键 check status 和人工确认的 score，不保存完整真实方案、完整 live analysis 或整个 API response。

当前覆盖：

- Plumbing review：general profile，CR-009 无应急证据时为 `NOT_APPLICABLE`。
- Scaffold review：special profile，进度章节存在但日期不可读时 CR-003 为 `PARTIAL`，明确计算书章节使 CR-014 为 `PASS`。

Existing V0.2 document-analysis Golden truth 保持独立且未修改。

## 12. Scope Boundary

V0.3 判断的是“方案应有内容是否存在、是否具有足够且可追溯的证据”。

V0.3 不判断：

- 是否满足具体规范条文
- 施工做法是否合法或正确
- 施工风险等级
- 专家论证结论
- 法规合规性

因此，完整性结果不能解释为规范条文结论、法规结论或施工技术正确性结论。

## 13. Known Limitations

1. OCR 未实现。
2. 图片化进度表或图片化章节可能无法从文本层提取，相关 completeness check 可能返回 `PARTIAL` 或 `MISSING`。
3. Generic profile 尚不能表达特定专业中的 mandatory applicability。例如某些深基坑、高支模工程中的监测或计算项目在专业层面可能属于必需内容，但当前 V0.3 只有 general/special profile。
4. CR-013 对部分通用标题仍有召回边界。“监测措施”等较泛化标题可能无法稳定归入工程监测语义；该问题尚未修复。
5. 超长嵌套文档的 completeness 结果继承 V0.2.1 chapter organization、main methods 和 structured extraction recall 边界。
6. Analysis cache 不存在时，为获得 `DocumentAnalysis`，系统仍可能调用外部 LLM。Completeness review 本身不调用 LLM。
7. 当前验收与监测检查采用保守 evidence policy，证据不足时可能返回 `PARTIAL`、`MISSING` 或 `NOT_APPLICABLE`，而不猜测内容存在。
